## Настройка автозапуска (Сравнение способов триггеров)

Для автоматического запуска пайплайна при пуше в Git существуют два основных подхода:

### Способ 1. GitHub Webhooks (Выбранный вариант)
* **Как это работает**: В настройках репозитория GitHub прописывается URL вашего сервера Jenkins. При каждом коммите GitHub отправляет мгновенный HTTP-запрос (webhook) на сервер Jenkins, сообщая о необходимости запустить билд. В пайплайне это включается директивой `githubPush()`.
* **Плюсы**: Мгновенный запуск (сборка начинается через секунду после пуша), полное отсутствие лишней нагрузки на сервер Jenkins и сеть.
* **Минусы**: Требует, чтобы ваш Jenkins-сервер имел публичный IP-адрес или был проброшен наружу (например, через `ngrok`), чтобы GitHub мог до него достучаться.

### Способ 2. SCM Polling (Опрос репозитория по расписанию)
* **Как это работает**: Jenkins настраивается с помощью cron-расписания (например, директива `pollSCM('*/5 * * * *')`). Каждые 5 минут Jenkins сам идёт на GitHub и спрашивает: «Появились ли новые коммиты?». Если появились — запускает билд.
* **Плюсы**: Работает даже на полностью изолированных серверах (например, на домашнем Mac за NAT или в закрытом контуре компании). Jenkins сам инициирует запросы, поэтому ему не нужен публичный IP.
* **Минусы**: Задержка старта (до 5 минут), постоянная трата сетевого трафика и процессорного времени на пустые запросы к GitHub, когда изменений нет.

### Почему выбран именно GitHub Webhooks:
Для промышленного CI/CD подхода критически важна **скорость обратной связи**. Разработчик должен сразу видеть статус своего коммита в Pull Request. Метод Webhooks обеспечивает моментальную реакцию системы, не нагружая инфраструктуру пустыми периодическими опросами, что делает пайплайн быстрым и чистым.
